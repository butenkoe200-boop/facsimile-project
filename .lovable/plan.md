# Pixel-perfect адаптация Travel Pay по PDF

## Цель
Воспроизвести 16 desktop-экранов PDF максимально точно, сохранив существующие маршруты, данные, формы, переходы, RU/EN-переключение и всю рабочую логику. PDF является единственным визуальным эталоном.

## Сопоставление PDF и сайта
1. Главная → `/`
2. Оплата картой → `/card`
3. СБП → `/sbp`
4. Яндекс Pay → `/yandex-pay`
5. Банковская рассрочка → `/installment`
6. Яндекс Сплит → `/yandex-split`
7. Обработка платежа → `/processing`
8. Успешная оплата → `/success`
9. Ожидание подтверждения → `/waiting`
10. Кредит предварительно одобрен → `/credit-approved`
11. Кредит не одобрен → `/credit-declined`
12. Выбор банка → `/credit`
13. Проверка заявки → `/credit-check`
14. Возврат после банка → текущее промежуточное состояние кредитного flow
15. Ошибка оплаты → `/error`
16. Спасибо → `/thanks`

Дополнительные существующие маршруты `/credit-form`, `/receipt`, `/receipt-email`, `/support`, `/profile` сохранят функциональность и будут приведены к той же визуальной системе без создания дубликатов.

## Что будет изменено
- Пересобрать общий desktop-каркас по A4 landscape-композиции PDF: верхняя полоса НТС, трёхзонная шапка, рабочая область шириной и пропорциями как в эталоне, полноценный многоколоночный подвал.
- Уточнить общие токены цветов, границ, теней, радиусов и типографики по PDF; использовать локальные шрифты и существующие локальные изображения/логотипы.
- Привести общие блоки к эталону: сводка заказа, заголовки, кнопки назад, защитные сообщения, наборы преимуществ, помощь и служебные элементы.
- Для каждого из 16 экранов воспроизвести его собственную сетку: реальные пропорции колонок, высоты секций, размеры карточек, иллюстраций, форм, банковских предложений, статусов и кнопок.
- Сохранить дополнительные рабочие состояния сайта, применив к ним согласованную PDF-систему без изменения содержания и поведения.
- Desktop сделать первичным визуальным совпадением; мобильную версию сохранить работоспособной и без переполнения, не превращая desktop в растянутый мобильный экран.

## Технические ограничения
- Не менять бизнес-логику, данные заказа, обработчики, API, формы, ссылки, маршрутизацию и providers.
- Не добавлять новые страницы вместо существующих и не объединять PDF-экраны.
- Переиспользовать `Header`, `Footer`, `OrderSummary`, `PageFrame`, брендовые и кредитные компоненты; уникальную разметку менять только внутри соответствующего маршрута.
- Все визуальные значения проводить через существующую систему токенов и Tailwind-классы.

## Проверка
- Снять эталонные изображения каждой страницы PDF и скриншоты всех соответствующих маршрутов при одинаковой desktop-пропорции.
- Выполнить два прохода сравнения по всем 16 экранам: сначала структура/сетка, затем размеры, отступы, типографика, цвета, границы, радиусы и позиционирование.
- Проверить дополнительные маршруты `/credit-form`, `/receipt`, `/receipt-email`, `/support`, `/profile` на визуальную целостность.
- Проверить 1280, 1440 и 1920 px: отсутствие горизонтального скролла, обрезки и наложений.
- Проверить мобильный viewport на отсутствие регрессий.
- Проверить все ключевые переходы, формы и кнопки, generated route tree, typecheck/build, console/runtime errors.
