# Pixel Perfect App

ЗАДАЧА: СОЗДАТЬ ТОЧНУЮ КОПИЮ ПРИЛОЖЕНИЯ ПО PDF «ВЫСОТКА»

В проект прикреплён PDF-файл «высотка». Это основной и обязательный источник требований к приложению.

Твоя задача — полностью воспроизвести приложение по PDF: визуально, структурно и функционально.

КРИТИЧЕСКОЕ ТРЕБОВАНИЕ

Мне нужна не интерпретация, не редизайн и не “похожее приложение”.

Мне нужна максимально точная копия интерфейса со скриншотов в PDF.

Ориентир:

PDF = Source of Truth.

Если какое-либо твоё дизайнерское решение отличается от того, что показано в PDF, приоритет всегда у PDF.

Не добавляй от себя новые элементы, не меняй композицию, не улучшай дизайн и не упрощай интерфейс без прямого указания.

1. СНАЧАЛА ИЗУЧИ PDF ПОЛНОСТЬЮ

Перед началом реализации:

Изучи весь PDF целиком.

Просмотри каждый скриншот.

Прочитай весь текст, описания, подписи и пояснения.

Определи все страницы приложения.

Определи все состояния элементов.

Определи всю навигацию между экранами.

Определи все интерактивные элементы.

Определи, какие элементы являются:

кнопками;

вкладками;

карточками;

полями;

селекторами;

переключателями;

меню;

модальными окнами;

ссылками;

элементами навигации;

списками;

фильтрами;

элементами управления.

Не начинай разработку поверхностно после просмотра пары страниц. Сначала разберись во всём PDF.

2. ВИЗУАЛЬНАЯ КОПИЯ 1:1 — ЭТО КРИТИЧНО

Необходимо максимально точно повторить внешний вид каждого экрана.

Для каждого экрана необходимо воспроизвести:

расположение элементов;

размеры;

ширину и высоту блоков;

отступы;

внутренние padding;

расстояния между элементами;

размеры кнопок;

радиусы скругления;

толщину границ;

цвета;

фон;

тени;

типографику;

размер шрифта;

насыщенность шрифта;

межстрочные интервалы;

выравнивание;

иконки;

изображения;

состояние активных элементов;

состояние неактивных элементов;

визуальную иерархию;

порядок блоков;

размеры карточек;

расположение нижней/верхней навигации;

фиксированные элементы;

прокрутку;

поведение контента.

ОСОБО ВАЖНО

Не используй принцип:

«Сделаем примерно так же».

Используй принцип:

«Нужно воспроизвести пиксельно максимально близко к референсу».

Если на скриншоте элемент находится на определённом расстоянии от другого элемента — сохрани это расстояние.

Если карточка имеет определённую высоту — сохрани её.

Если кнопка имеет конкретную форму — сохрани её.

Если блок расположен по определённой сетке — сохрани сетку.

3. НЕ ИЗОБРЕТАЙ СВОЙ UI

Запрещено самостоятельно:

менять дизайн;

менять цвета;

менять шрифты без необходимости;

переставлять блоки;

менять размеры;

добавлять дополнительные кнопки;

добавлять дополнительные поля;

удалять элементы;

менять названия;

менять тексты;

менять иконки на произвольные;

делать собственный вариант навигации;

делать «более современный» дизайн;

делать «более удобный» дизайн;

заменять сложный элемент упрощённым;

объединять несколько экранов в один;

создавать интерфейс по собственной логике, если она отличается от PDF.

Не улучшай дизайн.

Моя задача — получить именно ту реализацию, которая показана в PDF.

4. ВСЕ СТРАНИЦЫ ДОЛЖНЫ БЫТЬ РЕАЛЬНО РАБОЧИМИ

Критически важно: приложение не должно быть набором статичных макетов.

Все страницы из PDF должны существовать в приложении и открываться.

Проверь:

переходы между страницами;

кнопки;

вкладки;

меню;

карточки;

back-навигацию;

закрытие модальных окон;

открытие модальных окон;

переключение состояний;

фильтры;

селекторы;

поля;

формы;

скролл;

нижнюю навигацию;

верхнюю навигацию;

ссылки между разделами.

Если на экране есть элемент, который по смыслу должен открывать другой экран, он должен это делать.

Никаких dead buttons.

5. СОЗДАЙ ПОЛНУЮ НАВИГАЦИЮ

Составь внутри проекта карту всех экранов.

Условно:

Screen A
→ Screen B
→ Screen C
→ Screen D

и так далее.

Каждый переход должен быть реализован.

Если в PDF показан сценарий:

пользователь нажимает кнопку;

открывается экран;

пользователь выбирает элемент;

открывается следующий экран;

пользователь возвращается назад;

— этот сценарий должен полностью работать.

Не делай отдельные страницы, которые невозможно найти из интерфейса.

6. ЕСЛИ В PDF ПОКАЗАНЫ СОСТОЯНИЯ — РЕАЛИЗУЙ ИХ

Если один и тот же экран в PDF представлен в нескольких состояниях, это не разные случайные картинки.

Это разные состояния интерфейса.

Например:

active / inactive;

selected / unselected;

opened / closed;

empty / filled;

loading;

error;

modal opened;

filter applied;

expanded / collapsed.

Все такие состояния должны быть реализованы.

7. ДАННЫЕ И ФУНКЦИОНАЛЬНОСТЬ

Если для полноценной работы интерфейса нужны данные, создай необходимые mock/demo данные.

Но:

данные должны использоваться для демонстрации интерфейса и не должны менять внешний вид относительно PDF.

Если в PDF есть:

списки;

карточки;

пользователи;

объекты;

статистика;

значения;

статусы;

категории;

фильтры;

создай соответствующие данные, чтобы интерфейс выглядел и работал как на референсе.

Не оставляй страницы пустыми только потому, что backend ещё не подключён.

8. RESPONSIVE

Основной приоритет — точное соответствие PDF на том размере экрана, под который сделаны скриншоты.

Сначала добейся максимального визуального совпадения с референсом.

После этого обеспечь корректное адаптивное поведение там, где это необходимо.

Не допускай:

горизонтального overflow;

сломанных карточек;

наложения текста;

обрезанных кнопок;

выезжающих за экран элементов;

неправильной высоты экранов;

прыгающей навигации.

9. КОМПОНЕНТНАЯ АРХИТЕКТУРА

Несмотря на требование точной копии, код должен быть нормально организован.

Создавай переиспользуемые компоненты там, где элементы действительно повторяются:

Header;

Bottom Navigation;

Buttons;

Cards;

Inputs;

Tabs;

Filters;

Modals;

Lists;

Navigation elements;

повторяющиеся UI-блоки.

Но компонентизация не должна приводить к визуальным компромиссам.

Если два визуально похожих элемента имеют разные размеры или состояния в PDF — не объединяй их насильно в один универсальный компонент, если это ухудшает точность.

10. ИКОНКИ И ГРАФИКА

Используй максимально близкие к PDF иконки и графические элементы.

Не заменяй иконку случайным символом Unicode.

Не используй:

emoji вместо иконок;

случайные SVG;

приблизительные символы;

неподходящие icon packs, если они визуально отличаются.

Если необходимые изображения/иконки находятся в PDF или доступны в проекте — используй их.

Если невозможно получить оригинальный asset, создай максимально близкий визуальный эквивалент.

11. ТЕКСТЫ

Все тексты должны соответствовать PDF.

Не сокращай текст.

Не меняй формулировки.

Не переводи.

Не исправляй формулировки самостоятельно.

Не заменяй текст placeholder'ами вроде:

Lorem ipsum;

Test;

Example;

Button;

Text;

User;

Item.

Если в PDF указан конкретный текст — используй именно его.

12. НЕ ДЕЛАЙ PLACEHOLDER-ЭКРАНЫ

Мне не нужны экраны вида:

«Страница в разработке»

или:

«TODO»

или:

«Coming soon»

или пустые страницы.

Каждый экран из PDF должен быть реализован настолько полно, насколько это описано в документации.

13. СТРУКТУРА ПРОЕКТА

Перед реализацией определи:

список всех экранов;

маршруты;

компоненты;

состояния;

интерактивные элементы;

зависимости между экранами.

Затем реализуй приложение целиком.

Не делай только первый экран и не останавливайся.

14. ОБЯЗАТЕЛЬНАЯ ПРОВЕРКА ПОСЛЕ РАЗРАБОТКИ

После реализации самостоятельно пройди приложение как пользователь.

Проверь каждый экран из PDF.

Для каждого экрана проверь:

Визуально

соответствует ли расположение элементов;

соответствует ли размер;

соответствует ли отступ;

соответствует ли цвет;

соответствует ли типографика;

соответствует ли радиус;

соответствует ли тень;

соответствует ли иконка;

соответствует ли фон;

соответствует ли состояние.

Функционально

открывается ли экран;

работают ли кнопки;

работают ли вкладки;

работают ли фильтры;

открываются ли модальные окна;

работает ли back;

работают ли переходы;

работает ли scroll;

нет ли dead buttons;

нет ли ошибок.

15. ОСОБЕННО ВАЖНО: НЕ ОСТАНАВЛИВАЙСЯ НА «ВЫГЛЯДИТ НОРМАЛЬНО»

Фраза «примерно соответствует» здесь неприемлема.

Нужно сравнивать реализацию непосредственно с PDF.

Если элемент выглядит:

немного выше,

исправь.

Если:

немного шире,

исправь.

Если:

другой отступ,

исправь.

Если:

другой размер текста,

исправь.

Если:

другая иконка,

исправь.

Если:

другой радиус,

исправь.

Повторяй проверку до тех пор, пока интерфейс максимально близко не соответствует референсу.

16. ПРИОРИТЕТЫ

При принятии любых решений используй следующий порядок приоритетов:

1. PDF и его скриншоты

2. Текстовые требования внутри PDF

3. Функциональная логика, описанная в PDF

4. Работоспособность навигации

5. Корректность responsive-поведения

6. Качество и чистота кода

Не жертвуй визуальной точностью ради собственного дизайнерского решения.

17. НЕ ЗАПРАШИВАЙ ПОДТВЕРЖДЕНИЕ НА КАЖДЫЙ ШАГ

Если информации достаточно в PDF — принимай решение самостоятельно на основании PDF.

Не спрашивай:

«Как должна выглядеть кнопка?»

если это видно на скриншоте.

Не спрашивай:

«Какой должен быть отступ?»

если он очевиден из референса.

Не спрашивай:

«Какую страницу открыть?»

если логика описана в PDF.

Используй предоставленный PDF как спецификацию.

18. ФИНАЛЬНЫЙ РЕЗУЛЬТАТ

В результате я должен получить полностью рабочее приложение, в котором:

реализованы все страницы из PDF;

реализована навигация между страницами;

работают все основные интерактивные элементы;

реализованы состояния;

отсутствуют dead buttons;

отсутствуют пустые placeholder-экраны;

дизайн максимально точно соответствует PDF;

структура приложения соответствует описанной логике;

приложение можно полноценно пройти от начала до конца.

ФИНАЛЬНОЕ ТРЕБОВАНИЕ

Не воспринимай PDF как источник вдохновения.

Воспринимай его как готовое техническое задание и визуальный эталон, которому необходимо следовать максимально точно.

Мне нужна точная реализация существующего дизайна, а не твоя дизайнерская интерпретация.

Перед завершением обязательно:

перечитай PDF;

проверь все экраны;

проверь все переходы;

проверь все интерактивные элементы;

сравни визуально каждый экран с референсом;

исправь все найденные расхождения;

убедись, что приложение можно пройти целиком без тупиков.

Сначала полное понимание PDF → затем реализация → затем полный аудит всех экранов → затем исправление расхождений.

Не останавливайся на первом рабочем варианте. Цель — максимально точное соответствие референсу и полностью рабочая навигация по всему приложению.
